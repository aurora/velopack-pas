# Architecture

## Goal

Make [Velopack](https://velopack.io) (installer and auto-updater) usable from
Free Pascal / Lazarus **and** Delphi applications, including GUI applications,
as a reusable library.

## Approach

Velopack ships a native library with a stable C ABI (`vpkc_*` functions,
declared in `Velopack.h`). We do not port any Velopack logic. We:

1. translate the C header to Pascal,
2. wrap it in an idiomatic, memory-safe object API,
3. optionally add a non-visual component for GUI applications.

The deliverable is a **Pascal source library** (units + IDE packages). There is
no Pascal-built DLL; the only binary is Velopack's own native library, loaded
at run time.

Binding reference: `third_party/velopack/Velopack.h`
(taken from Velopack `master` on 2026-10-11, generated by cbindgen 0.29.4).

## Layers

```
 +-----------------------------------------------------------+
 | 4. Component        Velopack.Updater (RTL only, ADR 0008) |  threads
 +-----------------------------------------------------------+
 | 3. Object API       Velopack.App, .Manager, .Log          |  no GUI deps
 +-----------------------------------------------------------+
 | 2. Native binding   Velopack.Native, Velopack.Internal    |  no GUI deps
 +-----------------------------------------------------------+
 | 1. Foundation   Velopack.Compat.inc, Velopack.Strings,    |  no deps
 |                 Velopack.Types                            |
 +-----------------------------------------------------------+
 | Velopack native library (Rust, C ABI)                     |
 +-----------------------------------------------------------+
```

Dependency rule: a layer may only use layers below it.

| Unit | Responsibility |
|------|----------------|
| `Velopack.Compat.inc` | Compiler / platform conditionals shared by all units |
| `Velopack.Strings` | UTF-8 conversion helpers, the only place that converts `string` <-> C strings (ADR 0007) |
| `Velopack.Types` | Public records, enums, event types and the `EVelopackError` hierarchy |
| `Velopack.Native` | 1:1 translation of `Velopack.h`, loads the library, resolves exports |
| `Velopack.Internal` | Not public API: native <-> Pascal conversion helpers |
| `Velopack.App` | `TVelopackApp`: startup hooks, must run first in `main` |
| `Velopack.Manager` | `TUpdateManager`, `TUpdateSource`, `TUpdateInfo` |
| `Velopack.CustomSource` | `TCustomUpdateSource`: update sources implemented in Pascal (feed + download callbacks) |
| `Velopack.Log` | Bridge for native log messages |
| `Velopack.Updater` | `TVelopackUpdater`: asynchronous component, events on the main thread; RTL only |
| `packages/Velopack.Reg` | Palette registration, shared by the Lazarus and Delphi packages |

## Key design points

- **Dynamic loading** (ADR 0004): the application starts even when the native
  library is missing and can report this gracefully. A library path can be
  supplied explicitly or through the `VELOPACK_LIBRARY` environment variable.
- **One source base for FPC and Delphi** (ADR 0005): `{$mode delphi}` on FPC,
  conditionals centralized in `Velopack.Compat.inc`.
- **No threads in the core** (ADR 0006): blocking calls stay blocking;
  `TVelopackUpdater` runs them in a worker thread and marshals events to the
  main thread with `TThread.Queue`.
- **One component for every toolkit** (ADR 0008): `TVelopackUpdater` needs only
  the RTL, so LCL, VCL, FMX and console programs share it. The IDE packages
  (`packages/lazarus`, `packages/delphi`) only add registration.
- **Value semantics for assets**: `TVelopackAsset` is a record of managed
  strings. Native `vpkc_asset_t` structures are copied and freed immediately,
  so users never deal with native memory.
- **Booleans**: C `bool` maps to Pascal `Boolean`, never `ByteBool`
  (`True` would be 255, undefined behavior in C/Rust).
- **Errors become exceptions**: native failures are raised as `EVelopackError`
  carrying the message from `vpkc_get_last_error`.

## Threading rule for the updater component

Code that runs inside `CheckSynchronize` (the component's `Drain` method and the
events it raises) never waits for a thread. FPC's `TThread.WaitFor` pumps the
main-thread queue when called on the main thread (always on Windows, in a loop
on Unix), so waiting from a queued method re-enters the queue. Finished worker
threads are retired and freed later; `Destroy` sets a flag first so a re-entrant
`Drain` only discards messages and frees the update info they own. Both
failure modes were found by the Windows CI job and are covered by tests
(`DestroyWhileBusyIsSafe`, `DestroyWithUndeliveredResultDoesNotLeak`).

## Custom update sources

`TCustomUpdateSource` (events or overridable methods) lets an application serve
the release feed and the package download itself. The native library receives a
pointer to a small context object instead of the source, so freeing the source
before the manager makes the callbacks fail cleanly instead of crashing. Behavior
of the real library that the design and tests rely on (read from its source and
confirmed by tests): the feed is requested as `releases.<channel>.json`; `NULL`
from the feed callback is an error; the feed callback runs on the calling thread,
the download callback on a thread created by the library; progress 0 and 100 are
sent by the library, and progress of very fast downloads may not be delivered at
all because the library polls every 50 ms and stops when the download is done.

## Startup contract

`TVelopackApp.Run` must be called as the very first statement of the
program (before the GUI framework is initialized). Velopack invokes the
application with special arguments during install, update and uninstall and
expects the process to exit quickly; `Run` handles this and may not return.
If the native library is missing, `Run` returns `False` and the application
continues without update support.

## Out of scope (for now)

- Packaging: use the `vpk` CLI. We provide example scripts only.
